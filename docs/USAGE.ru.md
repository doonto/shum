# Установка и работа с Shum

Shum расшифровывает длинные MP3 на CPU: сохраняет версии ASR от выбранных локальных моделей, размечает говорящих локальной pyannote и, если настроен LLM-провайдер, сверяет тексты. Немецкий приводится к литературному немецкому, русский остаётся русским. Результат не заменяет проверку записи человеком: LLM получает текст, но не слышит аудио. Проект на ранней стадии; качество и время полного задания на вашей машине не гарантируются.

## Перед установкой

Нужен Linux (основной сценарий проверялся на Ubuntu), достаточно места для нескольких больших моделей и проектов, а также `ffmpeg`/`ffprobe`, Rust с `cargo`, `uv` и Python 3.11, доступный для `uv`. Для скачивания моделей нужен доступ к Hugging Face и утилита `hf` (Hugging Face CLI). Графический ускоритель не требуется: штатные адаптеры работают на CPU. Изоляция отдельных Python-окружений важна: зависимости NeMo, Whisper/Transformers, Qwen и pyannote устанавливаются по отдельности.

До установки модели pyannote примите условия на [странице Community-1](https://huggingface.co/pyannote/speaker-diarization-community-1) под своим аккаунтом и войдите через `hf auth login`. Установка модели без этого доступа может завершиться ошибкой. После локальной установки штатный адаптер диаризации не загружает аудио на сервер; LLM-проверка, напротив, отправляет **текст гипотез** выбранному провайдеру. Включайте её только если допускаете такую передачу.

## Обновление существующей установки

Дождитесь завершения работающих заданий Shum. Затем из каталога исходников
повторно запустите установщик с прежними путями. Для установки с обычным
расположением каталогов:

```bash
ROOT="$HOME/shum"
bash scripts/install.sh --storage-dir "$ROOT" \
  --bin-dir "$ROOT/bin" --settings-dir "$ROOT/config" \
  --projects-dir "$ROOT/projects" --models-dir "$ROOT/models" < /dev/null
```

Если каталоги разнесены, укажите их фактические пути. Установщик сначала
публикует runtime, соответствующий новому бинарнику, затем заменяет программу.
Он сохраняет проекты, окружения Python, ревизии моделей и настройки LLM,
создаёт резервную копию конфигурации и обновляет пути управляемых адаптеров.
Пользовательские адаптеры не заменяются. Без терминала эта команда не
скачивает модели или зависимости и не меняет файлы оболочки.

Не заменяйте только исполняемый файл: при отсутствии соответствующей версии
runtime запуск завершится ошибкой проверки целостности.

## Установка: исходники отдельно от данных

Из каталога исходников запустите установщик:

```bash
bash scripts/install.sh
```

Скрипт собирает переносимый релиз и запускает мастер настройки; `cargo build --release` **только собирает** программу. Выберите каталог установки вне дерева исходников, затем отдельные каталоги для исполняемого файла, личных настроек, проектов и моделей. Каталоги могут находиться на разных дисках. Мастер предложит зарегистрировать команду `shum` через ссылку в `~/.local/bin` (или в `~/bin`, если он уже есть в `PATH`). Если каталог программы отсутствует в `PATH`, мастер спросит разрешение на изменение файлов запуска Bash или Zsh. Если установленный `bin` уже есть в `PATH`, дополнительная ссылка не нужна. Исполняемый файл в исходниках не хранит за вас модельные снимки и настройки.

Для установки без диалога путей укажите **все пять** каталогов явно (пример с переменной, которую можно заменить своим абсолютным путём):

```bash
ROOT="$HOME/shum-local"
bash scripts/install.sh --storage-dir "$ROOT" \
  --bin-dir "$ROOT/bin" --settings-dir "$ROOT/config" \
  --projects-dir "$ROOT/projects" --models-dir "$ROOT/models"
"$ROOT/bin/shum" --help
```

Это бездиалоговая **настройка путей**, а не автоматическая установка всего: если нет терминала, мастер не спрашивает о Python-окружениях, моделях и LLM. Их нужно настроить отдельно в терминале. При установке с терминалом мастер спрашивает согласие на установку Python-зависимостей через `uv` (большие загрузки), затем предлагает выбор **для каждой** модели. Нажатие Enter оставляет роль без изменений; `latest` скачивает актуальный снимок, `pin REVISION` — названную ревизию, `pinned` — уже закреплённую. Ни запуск программы, ни `doctor`, ни проверка обновлений сами модели не скачивают.

Без диалога установка **не** добавляет команду в пользовательские каталоги и не правит `PATH` или файлы оболочки. Для явной регистрации добавьте к команде установки `--command-dir /абсолютный/каталог`; `--setup-shell` допускается только вместе с `--command-dir` и добавляет отсутствующий каталог в файлы запуска поддерживаемой оболочки. Лучше выбрать каталог, который уже есть в `PATH`. Чтобы исправить только регистрацию существующей установки, не переустанавливая её и не проверяя модели или LLM, вызовите установленный файл по полному пути:

```bash
"$ROOT/bin/shum" setup-command --command-dir "$HOME/.local/bin"
# Если каталог отсутствует в PATH и вы хотите сохранить его для новых оболочек:
"$ROOT/bin/shum" setup-command --command-dir "$HOME/.local/bin" --setup-shell
```

Без `--command-dir` команда ремонта выберет каталог установленного файла, если он уже в `PATH`; иначе — `~/.local/bin` (или `~/bin`, если он уже есть в `PATH`). При необходимости укажите `--installation "$ROOT"` **до** `setup-command`. Изменение профиля Bash затрагивает `.bashrc` и первый существующий `.bash_profile`/`.bash_login` либо `.profile`; Zsh использует `.zshrc` и `.zprofile` в `ZDOTDIR`, если он задан. Shum сохраняет прежнее содержимое и резервную копию, повторный запуск не дублирует настройку и не заменяет чужой файл или ссылку `shum`. Для **текущего** терминала выполните напечатанную команду `export PATH=...` или откройте новую оболочку: дочерний процесс не может изменить `PATH` родителя. Переход в каталог с файлом `shum` не делает его доступным как `shum`: `./shum` работает, потому что путь указан явно.

После подтверждения окружения располагаются под `<каталог установки>/runtime/environments/{primeline,flix,qwen,diarization}/`, а версии адаптеров — под управляемым `<каталог установки>/runtime/`. Внешние или экспериментальные адаптеры мастер не переустанавливает автоматически. Если окружения пропущены, повторите `shum --onboarding` в терминале и подтвердите их установку; ручная настройка одной роли описана в [руководстве ASR](../adapters/asr/README.md) и [руководстве диаризации](../adapters/diarization/README.md). Настройка моделей отдельно: `shum --setup-models` в терминале; каждый успешный выбор сохраняется сразу. Поддерживаемые штатные репозитории указаны в [шаблоне конфигурации](../shum.example.toml). Экспериментальные движки из README адаптеров нельзя включить одним переключателем: нужны проверенные веса, отдельное окружение и соответствующая настройка адаптера.

Настройки хранятся в выбранном `config/config.toml`, сведения об установке — в `config/settings.toml`; они не принадлежат репозиторию исходников. Если `shum` запущен отдельно от своего установленного `bin`, передайте `--installation "$ROOT"` или абсолютный путь к настройкам через `SHUM_SETTINGS`; установленный бинарник также умеет найти соседние метаданные установки. Первое обращение без готовых настроек в терминале предлагает мастер; без терминала программа сообщает, что требуется `--onboarding --storage-dir PATH`, а не ждёт ответа.

### Закрепление и проверка моделей

```bash
shum models check
shum models install-pinned --role qwen
shum models update --role qwen
```

`models check` проверяет локальные контрольные суммы и закреплённые ревизии **всех** ролей; доступность более новой версии на Hugging Face проверяется по возможности и не меняет модель. Если роль ещё не установлена, сначала выберите её через `--setup-models`; `install-pinned` требует уже указанной ревизии. `install-pinned` скачивает ровно её, `update` явно выбирает текущую ревизию из удалённого репозитория. Новая версия сначала загружается и проверяется в отдельном каталоге, затем активируется записью конфигурации; старая не перезаписывается. Если проверка целостности не прошла, не полагайтесь на такой снимок: переустановите конкретную роль.

### Оптимизированный локальный профиль ASR

После проверки на конкретной машине можно включить связку primeLine/ONNX FP32, Swiss German Whisper Turbo/CTranslate2 INT8 и Qwen3-ASR/llama.cpp Q8_0. Это отдельный профиль, а не новые настройки по умолчанию. Turbo занимает прежнюю роль `flix`; названия этапов и API остаются прежними.

Инструкции по окружениям, исходным снимкам и проверке производных весов находятся в руководствах [primeLine ONNX](../adapters/asr/primeline_onnx_README.md), [Turbo CTranslate2](../adapters/asr/turbo_README.md) и [Qwen GGUF](../adapters/asr/README.md). Все файлы движков, библиотек и моделей храните вне исходников. Нельзя обновлять только исходную ревизию, оставляя старый ONNX, CT2 или GGUF: весь профиль нужно подготовить и проверить вместе.

Для измеренного режима: primeLine — один процесс с шестью потоками; Turbo — три процесса по шесть потоков, beam 3, штатный fallback и VAD; Qwen — один сервер с 16 потоками и четырьмя одновременными запросами. `resources.sequential_asr_roles = true` исключает одновременную работу разных моделей, но сохраняет три процесса Turbo. Флаг `--sequential-asr` по-прежнему ограничивает каждую модель одним процессом.

Оставляйте резерв памяти не меньше 4 ГиБ. При работающем пользовательском systemd можно включить `supervise_asr_with_systemd`, задать `systemd_memory_limit_mib` и `systemd_swap_limit_mib = 0`: лимит swap распространяется и на дочерний сервер Qwen. Перед заменой сохраните бинарник и личную конфигурацию; прежние версии runtime и окружений оставьте для отката. Настройки LLM, диаризации и проекты не нужно заменять. Скорость не доказывает точность: для её оценки нужна эталонная расшифровка.

### LLM: можно отложить

В мастере выберите `codex`, `copilot`, `custom` либо `skip`. Для штатных провайдеров установите соответствующий CLI и войдите **его** командой входа; Shum может предложить запустить вход для выбранного CLI, но не хранит его токен. Для `custom` задайте исполняемую программу, аргументы проверки в виде JSON-массива и аргументы запроса в том же формате; запрос поступает на stdin, техническая проверка должна ответить `SHUM_READY`. Параметры `{output}` и `{model}` доступны для аргументов. Не предполагайте, что `gh auth status` заменяет проверку доступа Copilot CLI. Проба посылает фиксированный технический запрос без данных проекта, но может расходовать квоту.

При проблемах с доступом мастер позволяет сохранить провайдера в нерабочем состоянии либо отключить проверку. Позже запустите `shum --setup-llm`, восстановите вход выбранного CLI и продолжите проект — заново выбирать каталоги и скачивать модели не нужно. Перед полным конвейером или LLM-этапами Shum проверяет доступность провайдера (с возможным кэшированием), в терминале может предложить исправить вход, а при недоступности выводит предупреждение; локальные этапы `project run` не требуют этой проверки. При сохранённой, но недоступной LLM проверка проекта ждёт внешнего сервиса, не выдавая черновик за итоговый текст.

`shum doctor` проверяет `ffmpeg`, `ffprobe`, скрипты и интерпретаторы
адаптеров, а также локальную целостность **каждой** модели из конфигурации,
включая произвольные ASR-роли и диаризацию. Для проверки не нужны `hf`,
сеть или доступ к LLM. Это **не** тест качества модели и не проверка
аудиоинференса. Если `doctor` сообщает о повреждённых весах, восстановите
точную закреплённую ревизию модели.

## Полная расшифровка и сохранение проекта

Чтобы не запускать Qwen, выберите только нужные ASR-роли:

```bash
shum transcribe /absolute/path/recording.mp3 --output meeting --asr primeline,flix
shum project resume meeting --asr primeline,flix
# Можно использовать одну модель:
shum transcribe /absolute/path/recording.mp3 --output single --asr primeline
```

Каждый запуск без `--asr`, в том числе `resume`, `run` и `rerun`,
использует **все роли из текущей личной конфигурации**. Флаг действует
только в этом запуске. История проекта хранит фактически выбранные роли,
но не задаёт набор по умолчанию для следующего запуска.
Роли `primeline`, `flix`, `qwen` остаются совместимыми со старыми настройками;
`flix` означает настроенную роль, в том числе
Turbo в оптимизированном профиле. Вычитка получает только выбранные
гипотезы. Готовые результаты ASR не удаляются; при смене набора
пересчитываются зависимые вычитка и экспорт. Чтобы снова включить Qwen, достаточно следующего запуска без флага,
если роль осталась в конфигурации.

Чтобы использовать одну модель, оставьте в личной конфигурации одну
секцию `[asr.ID]`, соответствующую запись `[[models]]`, модель
`diarization` и оценку памяти для этого ID. Другие ASR-роли не нужны.
Чтобы добавить модель, создайте в личной конфигурации `[asr.ID]` и ровно одну запись
`[[models]]` с `role = "ID"`; для новой роли укажите `engine = "nemo"`,
`"whisper"` или `"qwen"`. Движок и адаптер должны поддерживать формат весов:
`adapters/asr/main.py` не умеет загружать произвольную модель Hugging Face.
Можно настроить несколько ID с одним движком, например `meeting_whisper`
и `interview_whisper` с `engine = "whisper"` и разными совместимыми весами.
Число ASR-ролей не ограничено тремя. Удаление обеих записей отключает
роль; модель диаризации оставьте в единственном экземпляре.
Идентификатор состоит из латинских букв, цифр, `_` и `-` и не
должен совпадать с именем служебного каталога (`clips`, `reviews`, `exports`
и др.). Пример дополнительной роли есть в [шаблоне](../shum.example.toml).
Личную конфигурацию и веса не сохраняйте в исходниках.

Флаг не меняет уже работающий процесс. Если он долго распознаёт Qwen,
остановите его через Ctrl+C и продолжите тот же проект с новым набором.
Этап `asr:qwen` при исключённом Qwen требует явного включения этой роли.
Сохранённое ожидание ресурсов после OOM исключённой роли не блокирует
продолжение; при её включении проверка доступных ресурсов снова действует.

```bash
shum transcribe /absolute/path/recording.mp3 --output meeting
shum project status meeting
shum project resume meeting
```

`transcribe` принимает MP3. `--output` задаёт имя каталога **внутри выбранного каталога проектов**; абсолютный путь допустим только внутри него. Без `--output` имя строится из имени MP3. Для нового проекта выбирайте новое имя, не записывайте другой звук поверх существующего проекта. `--sequential-asr` уменьшает параллелизм ASR до одного процесса; выбранные роли при этом сохраняются. Обычный планировщик допускает параллельную обработку по оценкам свободной RAM. В секции `[resources]` `max_asr_workers` ограничивает общее число процессов, необязательный `max_parallel_asr_models` — число одновременно активных разных ID, а `sequential_asr_roles` запускает разные модели по очереди. Для каждого активного ID задайте `estimated_peak_mib`; оценки для отключённых исторических ID можно оставить. Резерв и оценки потребления не гарантируют защиту от OOM. Подробнее об ограничениях ресурсов — в [README](../README.md).

`project status` печатает JSON со статусом каждого этапа (`not_started`, `running`, `ready`, `failed`, `pending_external`, `stale`), числом попыток и предупреждениями. `resume` продолжает невыполненное и использует проверенные результаты уже готовых этапов. Если MP3 перемещён, укажите его новый путь:

```bash
shum project resume meeting --input /new/location/recording.mp3
```

Программа сверяет SHA-256 с исходной записью и откажется продолжить проект с другим содержимым. Переносите **всю директорию проекта**, включая `workflow.json`, `manifest.json` и промежуточные файлы; после переноса указывайте новый путь к проекту и, если нужно, `--input` к тому же аудио. Одновременная запись двумя процессами в один проект запрещена.

Внутри проекта находятся `audio.wav`, `chunks.json` и `clips/`, сырые ответы в каталогах с именами ASR-ролей, `diarization.json`, `review-flags.json`, `reviews/`, а после удачного экспорта — файлы с именем исходного аудио: для `recording.mp3` это `recording.txt` и `recording.json`, даже если проект называется `meeting`. Имя сохраняется при переносе или переименовании записи через `--input`. Если JSON-имя совпадает со служебным файлом проекта (например, `workflow.json` или `manifest.json`), оба итоговых файла лежат в подпапке `exports/`. CLI печатает полный путь к тексту, API возвращает пути в `exports.txt` и `exports.json`. Старые `transcript.*` при следующем `resume` или `rerun --step export` архивируются; повторно выполняется только экспорт при действительных предпосылках. В JSON есть временные метки, говорящие, исходные версии выбранных ASR, признаки пропусков и происхождение модели. Отметки `review-flags.json` помогают найти подозрительные окна, но не доказывают, что в аудио тишина. Проверяйте спорные места на слух. Папка проекта содержит приватные аудио и текст; не публикуйте её целиком.

| Код завершения `transcribe` / `project run` / `project resume` / `project rerun` | Значение |
| --- | --- |
| `0` | Получен полный экспорт `<имя аудио>.txt`/`<имя аудио>.json` либо успешно выполнен выбранный этап `project run`; частичный проект ещё не означает готовую расшифровку. |
| `1` | Ошибка команды, входных данных, окружения или локального этапа; уже записанный прогресс не нужно удалять, проверьте `project status` и исправьте причину. |
| `2` | Локальные результаты записаны, но LLM-проверка ожидает доступа либо не завершилась; окончательный экспорт не обещан. Исправьте провайдера и выполните `project resume`. |
| `3` | Работа заблокирована пропуском обязательного этапа или отсутствием доступных ASR-гипотез; финальный экспорт не создан. |
| `130` | Пользователь прервал проект через Ctrl+C; сохранённые результаты доступны для продолжения. |

### Этапы и повторный запуск

Порядок зависимостей: `audio` → `chunks` → независимые стадии `asr:ID` для активных моделей из конфигурации; `diarization` зависит только от `audio`. Далее `review-flags` использует доступные ASR-гипотезы и диаризацию, `review` требует флаги и LLM, `export` требует готовую проверку. Явно пропущенные ASR не создают пустых гипотез; без единой гипотезы экспорт заблокирован.

Чтобы выполнить **только выбранный этап и недостающие предпосылки**, не запуская последующие стадии, используйте `project run`. Для нового проекта передайте его будущий каталог и MP3 через `--input`; для уже созданного проекта достаточно имени каталога, а `--input` понадобится лишь после переноса записи:

```bash
shum project run meeting --step audio --input /absolute/path/recording.mp3
shum project run meeting --step asr:flix
shum project run meeting --step diarization
shum project run meeting --step review-flags
shum project status meeting
shum project resume meeting
```

Для `asr:flix` нужны `audio` и `chunks`, но не остальные ASR и не диаризация. Для `diarization` нужен только `audio`; `review-flags` ждёт активные локальные этапы. `run --step review` вызывает LLM, если локальные предпосылки готовы, а `run --step export` запускает недостающие предпосылки вплоть до полного результата. `project run` использует годные контрольные точки, а не повторяет их принудительно. После частичной стадии итогового `<имя аудио>.txt` ещё может не быть; смотрите `project status` и запускайте нужную следующую стадию либо `resume` для всего конвейера.

LLM может вернуть чистый JSON либо один полностью ограждённый блок
`json` (или блок без метки языка), без пояснений снаружи. Shum снимает
только эту обёртку и применяет прежние проверки схемы, индексов, языка,
текста и пропусков. Несколько блоков и JSON среди произвольного текста
отклоняются. Исходный ответ сохраняется отдельно в файле
`*.response-*.txt` рядом с ответом вычитки, с правами `0600`, в том числе
при ошибке проверки. После исправления провайдера продолжите проект
через `project resume`; повторное ASR не требуется.
Это работает и для ограждённого ответа, уже сохранённого старой версией:
`resume` проверяет его без нового запроса к LLM, сохраняет оригинал
и заменяет кэш чистым JSON только после успешной проверки всей партии.

```bash
shum project rerun meeting --step asr:flix
shum project rerun meeting --step diarization
shum project rerun meeting --step review
shum project rerun meeting --step export
```

`rerun --step` архивирует предыдущие результаты выбранного этапа и помечает **зависимые последующие этапы** устаревшими; затем запускает обычный конвейер до конца. Это **не команда «выполнить только один этап»**: повтор Flix не запускает primeLine или Qwen при действительных контрольных точках, но заново запустит проверку и экспорт; повтор диаризации не запускает ASR при действительных результатах; повтор `export` использует уже проверенный текст. Смена LLM делает устаревшими проверку и экспорт, но не ASR. Сохранённые попытки лежат в `attempts/`; после прерывания `resume` продолжает доступные результаты, включая завершённые окна и партии проверки.

## План выполнения и ручное управление

`shum project plan PROJECT` показывает известные этапы, их зависимости,
попытки и текущий выбор результатов. `shum project events PROJECT --after N`
возвращает журнал событий после номера `N`: при переподключении клиента
сохраните последнюю полученную последовательность. Ответ API
`project.events` содержит курсор `next_after`: передайте его в следующий
запрос как `after`. Команда CLI печатает только массив событий, поэтому
для неё используйте `sequence` последнего обработанного события.
Проценты относятся только к известному плану вычислений, **не к точности
расшифровки**. Если оценить длительность пока нельзя, программа должна
показывать неизвестное время, а не выдуманный процент или ETA. Параллельные
попытки завершаются не по порядку; повтор и добавление проверки меняют план
и оценку оставшегося времени.
Во время диаризации `get_embeddings` прогресс берётся из существующего
хука pyannote: число обработанных пакетов `completed` из `total`.
Например, ResNet на CPU с четырьмя потоками и размером пакета 1 может
обрабатывать их долго. Пока хук не сообщил новое значение, это **не
признак зависания**; программа не должна подставлять выдуманный процент.
Счётчик пакетов не оценивает точность назначения говорящих.

Для ASR одного ID терминал оценивает оставшиеся известные фрагменты по
наблюдаемой скорости, включая параллельных исполнителей. После расширения
плана он собирает новые измерения. Для разных моделей и неизмеренных
внешних запросов общая ETA пока остаётся неизвестной; время загрузки
и ожидания показывается отдельно, без выдуманных процентов.

Ручной запрос можно проверить командой `shum project control-preview
PROJECT --request /absolute/path/request.json`, затем отправить
`shum project control PROJECT --request /absolute/path/request.json`.
Файл содержит объект версии 1 с `request_id`, `expected_revision` из
`project plan`, `initiator`, `reason`, `evidence`, `confirmed` и помеченным
полем `action`; пример есть в [описании API](API.md#plans-progress-and-manual-controls).
Запрос должен явно подтверждать потенциально опасный пропуск; предварительный
просмотр не выполняет действие. Ограничения на число попыток и расширение
графа защищают от бесконечной работы, но не выбирают лучший текст и не
доказывают его правильность. Управление проектом не меняет личную
конфигурацию моделей и провайдера. Пропущенная обязательная подготовка
блокирует зависимые этапы; пропуск диаризации оставляет ограничение
качества, а пропуск LLM не даёт проверенного финального текста. Даже если
все запланированные вычисления завершились, проверяйте состояние экспорта
и отмеченные ограничения.
По умолчанию автоматическая работа ограничена тремя попытками и 600
секундами на проект, включая дополнительные проверки. Счётчики
сохраняются при возобновлении. Восстановление после OOM записывает решение
правила `resource-recovery` и обрабатывает только недостающие фрагменты;
предыдущая попытка и сохранённые результаты остаются в истории.
`resume` не отменяет ручной пропуск: отправьте действие `restore`
через `shum project restore PROJECT --request /absolute/path/request.json`,
затем продолжите проект.

При работе в терминале нажмите `s`, чтобы выбрать активную попытку
по номеру. Затем `c` отменяет именно попытку, а `s` пропускает логический
этап. Действие вступает в силу только после отдельного подтверждения
`y` и Enter; отказ не меняет план. Ctrl+C прерывает проект, но не меняет
личные настройки (в том числе при открытом запросе подтверждения).
Esc закрывает запрос без действия. Стрелки вверх и вниз, PageUp,
PageDown и Home прокручивают историю; изменение размера терминала
перерисовывает экран. В конвейере без терминала интерфейс не использует
ANSI-управление экраном; `NO_COLOR` отключает цвет, `TERM=dumb`
оставляет простой вывод. API всегда пишет в stdout только JSON.

## Локальная диагностика без моделей

При обычном запуске Shum обновляет отдельный отчёт `.quality/report.json`
в проекте. Проверки измеряют уровень аудио, отмечают возможный клиппинг,
повторы и расхождения ASR, проблемы координат и записанные ресурсные сбои.
Они не меняют текст, не обрабатывают звук, не запускают повторное
распознавание и не обращаются к LLM или сети.

```bash
shum project check-quality meeting
# Отключить автоматическую диагностику только для этого запуска:
shum --no-quality transcribe /absolute/path/recording.mp3 --output meeting
```

Для постоянного отключения задайте `enabled = false` в секции `[quality]`.
Явная команда `check-quality` работает и при отключённой автоматике:
она заново проверяет подготовленное аудио и доступные результаты.
Отсутствующие этапы не запускаются. Код завершения 0 означает, что
диагностика выполнена, в том числе частично; 1 — ошибку самой диагностики.
Предупреждения не запрещают экспорт.

В отчёте разделены выполнение проверок, покрытие данных и неизвестная
точность текста. Пустой ответ не доказывает тишину, совпадение моделей
не доказывает правильность. Пороговые значения — предварительные
настраиваемые эвристики. Рекомендации требуют проверки и не исполняются.
Отчёт перечисляет активные `asr_roles`: результаты отключённых ролей
отмечаются как `skipped_roles`, а не как `missing_roles`. Даже если
работает одна модель, `accuracy_status` остаётся `unverified`.
Текстовая проверка каждого окна указывает `source_status`:
`no_sources` при отсутствии гипотез, `single_asr_source` для одной
и `multiple_asr_sources_unverified` для нескольких. Одна гипотеза
не подтверждена другой моделью; совпадение нескольких не доказывает
точность или независимость моделей. Подсказка для LLM-проверки прямо
указывает на эти ограничения.
Вычислительные лимиты диагностики, например `quality.max_chunks`
и `quality.text.max_hypotheses`, ограничивают только отчёт: число
моделей в конвейере и набор гипотез для вычитки и экспорта от них
не зависят. Текстовая проверка рассчитывает показатели для **каждой**
доступной модели. Параметр `quality.text.max_hypotheses` по умолчанию
равен 8 и ограничивает только попарные сравнения. Если моделей 12,
отчёт содержит 12 наборов показателей, 28 сравнений первых восьми
и четыре ID в `pairwise_omitted_roles`. Причину указывает
информационная отметка `pairwise_hypothesis_budget`.

По умолчанию измеряется не более 1800 секунд аудио и 120 миллионов
sample frames; декодирование исходных каналов ограничено 60 секундами
выполнения. При достижении лимита отчёт показывает частичное покрытие.
Настройки находятся в `[quality.audio]`: `max_scan_seconds`,
`max_sample_frames`, `max_decode_seconds`, `near_zero_threshold`
(амплитуда 0,001 от full scale), `full_scale_threshold` (0,999)
и `low_rms_dbfs` (−50 dBFS). Это не граница слышимости речи.
Исходные каналы измеряются после декодирования в PCM16 с исходной
частотой дискретизации; файл и рабочая mono-запись не изменяются.

Текстовые проверки по умолчанию отмечают долю повторных четырёхсловных
последовательностей больше 0,5, серию из четырёх одинаковых слов,
плотность вне диапазонов 0,5–5 слов или 2–35 символов в секунду
и попарное сходство токенов меньше 0,5. Короткие реплики и естественные
повторы тоже могут вызвать предупреждение. Полная действующая политика
сохраняется в поле `policy` отчёта; она не служит оценкой WER/CER.

Для экономии ресурсов автоматический анализ аудио использует кэш
по размеру и времени изменения файла; явная команда перечитывает аудио.
Сводка сохранённого отчёта в `project status` не подтверждает его свежесть.
Для API доступны `project.check_quality` и постраничное чтение
`project.quality_report`; параметры описаны в [API.md](API.md).
При сбое диагностики программа явно сообщает об ошибке и сохраняет
доступные результаты транскрипции. Добавление отчёта не сбрасывает
старые ASR/LLM-чекпойнты и не меняет имена итоговых файлов.

## Как сравнивать скорость без ложных выводов о качестве

Штатные CLI-модели и экспериментальные ускоренные движки — разные профили; не меняйте рабочую конфигурацию по одному числу скорости. Для воспроизводимого теста используйте одну запись длиной не менее 30 минут: Shum берёт первые 1800 секунд, готовит 67 перекрывающихся окон (до 28 секунд, перекрытие 0,8 секунды), затем измеряет **загрузку модели вместе с обработкой всех окон**. Подготовка аудио, LLM и сборка общего результата не входят в это время. Для каждого движка и каждой из трёх свежих попыток нужна новая папка результатов; проверьте `benchmark.json`, полный счёт окон, отсутствие повторного использования кэша и время строго **меньше 600 секунд** в каждой попытке. Диаризация измеряется отдельной командой.

```bash
shum benchmark-asr /absolute/path/recording.mp3 --role primeline --output bench-prime-1
shum benchmark-asr /absolute/path/recording.mp3 --role flix --output bench-flix-1
shum benchmark-asr /absolute/path/recording.mp3 --role qwen --output bench-qwen-1
shum benchmark-diarization /absolute/path/recording.mp3 --output bench-dia-1
```

Учитывайте RAM, swap и завершение по OOM; не считайте остановленный или неполный прогон успешным. При сравнении альтернатив подтверждайте исходный репозиторий, ревизию и контрольные суммы преобразованных весов, фиксируйте точный адаптер, аргументы, число процессов и ограничения памяти. Отдельно прослушайте спорные окна, особенно возможные пропуски короткой речи: скорость, совпадение текстов и детектор повторов **не** подтверждают точность. Сводка последних проверенных и незавершённых экспериментов, включая три свежих прогона primeLine ONNX и Qwen GGUF, приведена в [таблице README](../README.md#cpu-engine-comparison-on-one-recording); метод и ограничения — рядом с ней. Эти экспериментальные профили не стали штатными настройками, а скорость полного проекта в пределах 10 минут не доказана.
